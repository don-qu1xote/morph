# ADR-0008: Очередь yt-dlp и быстрый клиент

## Статус

Принято.

## Контекст

Трек с YouTube начинал играть через несколько секунд после клика, а через VPN
ещё дольше. Время уходило на три вещи:

- yt-dlp по умолчанию опрашивает три клиента YouTube (`tv_samsung`,
  `visionos`, `web`) и для двух из них запускает deno, чтобы решить
  JS-задачку плеера;
- предзагрузка следующего трека стартовала в тот же момент, что и поиск
  текущего, и отнимала у него процессор и сеть;
- клик по треку, который уже искался заранее, запускал второй такой же
  процесс.

## Решение

- Поток сначала ищется только клиентом `visionos`: ему не нужен JS-плеер,
  это один запрос без deno. Если он ничего не отдал (детский контент,
  проверка на бота), тот же запрос повторяется с настройками по умолчанию.
  После трёх промахов подряд быстрый путь до перезапуска не пробуется.
  Переменная `MORPH_YTDLP_FAST` подменяет или выключает его без пересборки.
- У каждого трека не больше одного процесса yt-dlp. Включённый трек
  ищется сразу, предзагрузка ждёт, пока ничего не ищется. Клик по треку из
  очереди предзагрузки запускает его немедленно.
- `ServiceManager::prefetch` ищет следующий трек заранее. Если поток пришёл
  с YouTube, трек сразу качается в кэш и потом стартует с диска.
- Ошибка заранее найденного трека не показывается: если трек включат, поиск
  повторится и ошибка появится тогда.
- В QML файл из кэша важнее запомненной ссылки, ссылка YouTube с истёкшим
  `expire` не используется, а при ошибке плеера поток один раз ищется заново
  для любого сервиса, а не только для SoundCloud.

## Последствия

- В обычном случае поток находится одним запросом, без deno.
- Если YouTube закроет быстрый клиент, первые три трека потеряют время на
  промах, дальше всё идёт по-старому. Вариант можно поменять переменной, а
  `scripts/ytdlp-bench.sh` показывает, какой быстрее в конкретной сети.
- Предзагрузка тратит трафик на трек, который могут пропустить. Качается
  только следующий трек и только если включён кэш треков.
